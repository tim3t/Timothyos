## Captain's Log

Notion DB `NOTION_LOG_DATABASE` (Name = "Wednesday, October 7, 2026", Date, Source: Diary import / Bridge); the entry is the page body, one paragraph block per paragraph (blank lines separate them; `logParas_()` and the app's `logNorm()` must stay identical). The journal is Timothy's most private data: **never put entry text in the repo, tests, commits or chat summaries**, never cache it in the bridge, never store it on the iPad beyond `tos.ldraft.v1` (unsaved writing only, deleted once saved), and **never give the ASK button a path to it** (Log Ask, 2.15, reads only entries Timothy picks in the open LOG, with the PIN and caps). `bridge_log.test.js` asserts Ask's code doesn't call the log. App: `lg` state, `lockLog()` (called by `go()` entering or leaving LOG, `visibilitychange` hidden, `enterStandby()`, 10 min idle; flushes unsaved writing first), `renderLog()`, `logSave(pin)` (5 s debounce), `parseDiary()` for imports (headers like "Thursday, November 13, 2025"; same parser checked against the real export once, locally, never committed). `render()` skips redrawing LOG while its textarea has focus. The daily intent is `#logIntent` in ORDERS OF THE DAY and the bearing a COMMS row (2.63; INTENT + BEARING before). Tests: `mock_v20.py` (PIN 135790) + `app_e2e22`.

**Log Ask** (app 2.15, bridge 1.20, Timothy's request): PIN-gated actions in `logAction_()`: POST `logask` `{pin, scope: {from, to} | {dates[]}, mode: fast|deep|summary, messages[{role,text}], context?, preview?}`; `logasksave` `{insight: {title, question, scope, text}}`; `loginsights`; `loginsight` `{id}`. `logAskEntries_()` reads the entries (the one-line Search Text copy when present, else the page), refusing more than 62 entries or a range over 62 days (`log_ask_too_big`); `logAskEstimate_()` (about 3.6 chars per token; the entries are written to the prompt cache) refuses over 60K tokens. The entries are the first block of the first user turn with `cache_control`, so follow-ups read them from the cache; no tools; `LOG_ASK_RULES` asks for `[yyyy-mm-dd]` citations (the app turns them into buttons). Spend goes through `aiAddSpend_()`/`aiPaused_()`, logged as `log` / `logsummary` with no text. Never cache replies or entries on the bridge (unlike `ask_`). Insights are undated pages in the Log database with Source "Claude insight" (`LOG_INSIGHT`), which every date-based log query skips; `loginsight` opens only those. Capability `logask` = API key + Notion. App: `LS_LOGAI` toggle (Systems, Captain's Log section); `lg.ai` (scope, preset, q, deep, preview, msgs, insights, open), `logAiHtml()` in the page column, `logAiPreview()`, `logAiSend()`, `logAiSave()`; `LOG_AI_PRESETS`; a new search hides the panel (`lg.ai.view`). REVIEW: `writesummary` → `openSummaryAuth()` (code panel in `#detailScrim`, `lsum`) → `writeSummary(pin)` → `logask` mode summary for that week; WITHOUT THE LOG → the old `ask` summary. The ASK button (`ask_`) still has no path to the log; `bridge_logask.test.js` checks that, the caps, caching, spend and insights. Tests: `mock_v22.py` + `app_e2e31`.

**Bulleted lists** (app 2.14, bridge 1.19): a line starting `• ` or `- ` is a list item. Bridge `logParas_()` returns `[{type: paragraph|bulleted_list_item, text}]`; `logJoin_()` reads blocks back (list items joined by one newline, everything else by a blank line); the app's `logNorm()` must produce exactly that canonical text or every entry looks changed. `logSave_()` matches old and new blocks by type and plain text (`raw`), patches only changed ones in place, and replaces from the first type change on. Editor: `bulOnInput()` ("- " → "• "), `bulOnKey()` (Return carries the bullet; on an empty bullet ends the list), `bulToggle()` via `[data-bul]` chips (acts on pointerdown so the textarea keeps focus); edits go through `bulReplace()` (execCommand for undo, direct set as fallback). Applies to `clText-*` and `[data-rv]` textareas. REVIEW stores bullets as text in its rich-text properties. Tests: `bridge_log.test.js` (round trip, minimal patches), `mock_v22.py` `logcanon()` + `app_e2e30`.

**Log authorization** (app 2.12, bridge 1.17): `LOG_PIN` may be six digits or a code word from `LOG_WORDS` (ALPHA BETA GAMMA DELTA THETA OMEGA) and four digits; `logCode_()` normalizes any spelling (`omega 0451`, `Ω0451`) to `OMEGA-0451`, which is what the app sends as `pin`. Capability `logcode` tells the app to show the word keys (`cl-words`) before the keypad; the chosen word is shown only as the `.cl-dots i.w` slot, never by name. `logGate_()`: five misses lock via Script Properties `LOG_LOCK_UNTIL` (returned as `until`) for 15 min × 2^`LOG_STRIKES` (cap 24 h); a correct code clears both. Never store the code on the iPad. Tests: `bridge_log.test.js` (code formats, escalation), `mock_v22.py` `?action=pincode` + `app_e2e27`.

**Log search** (app 2.11, bridge 1.16, approved by Timothy): each Log page also holds its text, whitespace collapsed to one line, in a rich-text property `Search Text` (`LOG_SEARCH_PROP`; `·` marks an entry with no text). `setup()` adds the property via `PATCH /data_sources/{id}` (`logSearchSetup_()`) and sets Script Property `LOG_SEARCH_READY`, which turns on capability `logsearch`; until then saves and imports leave the property out (`logSearchProps_()`). Actions (PIN-gated like the rest of the log): GET `logsearch` `q` `whole` (1/0) → `entries[{date, count, snips}]` newest first, `mentions`, `left` (entries not yet indexed, counted to 100), `more`; a snippet is `[text, match, text, match, …, text]`, two per entry at most. Notion narrows with an `or` of case variants on `contains`, then `logSearchRe_()` applies case-insensitive matching and the exact-word rule (Unicode lookarounds). POST `logindex` (dry run counts what's left; `run: 1` fills up to 20 s of entries, newest first, under the script lock so a save is never overwritten; `busy` when Notion asks to slow down). `buildLogSearch()` does five minutes from the editor. App: `lg.find` (`q`, `whole`, `res`, `view`), `lg.whole`, `lg.idx` (progress, painted in place by `logIdxPaint()`), `logFind()`, `logFindHtml()` (results in the page column), `logFindBar()` (RESULTS / NEWER / OLDER over an entry), `logIndexStart()` → `logIndexStep()` after unlock. Nothing searched or found is stored on the iPad. Ask still has no path to the log or its search; `bridge_logsearch.test.js` checks that, plus the setup, index and match rules. Tests: `mock_v22.py` (port 8103) + `app_e2e26`.

## LOG → SESSIONS (app 2.51, bridge 1.35, D57)

Timothy's request; he confirmed the mockup and eight postulates 2026-10-28. 🛋️ Session Notes (`NOTION_SESSIONS_DATABASE`, created by Claude with his approval in the Life Hub beside the Captain's Log): Session (title "Solo · Wednesday, October 28, 2026"), Type Solo / Couples, Date, Where, Topics (multi-select, options made on write; commas become spaces), Arriving and Leaving (1 to 5), Felt, What Landed, Phrase, Bring Up Next Time, Next Session, Data (JSON `{v, onMind, notes{topic: text}, practice[], carried[{text, did}]}`). The page body is a readable copy (`sesBody_`), deleted and rewritten on each save; Data is what the app reads. Every action is named `logsession*`, so `doPost`/`doGet` route it to `logAction_` and `logGate_` checks the code (and counts misses) like the journal; nothing is cached except a new page's id under its cid. **App:** `logTab` ("journal" / "sessions", outlives a lock) and the inner module `sess` (CSS `sx-`); everything read lives in `lg.sn`, so `lockLog()` drops it. `sess.tabs()` sits at the top of the open LOG (only with `canSessions()`); the header reads SESSIONS · OPEN / LOCKED. Views in `lg.sn.view`: list (tree `type` > `type+year` > `type+yearQn`, open state in `lg.sn.open`, defaults: types open, the newest year and its newest quarter), one, form, suggest. The draft (`LS_SNDRAFT`, the only session data on the iPad; in `bkDrafts`, never in `BK_KEYS`) is written by `keep()` on every input, from fields with fixed ids (`sxDate`, `sxMind`, `sxNote-i`, `sxLanded`, `sxPhrase`, `sxNextT`, `sxNextD`). A new session copies the type's last practice into `carried` and shows its `nextTime`. SUGGEST TOPICS needs `canSesAsk()` (`sessionsuggest` and `LS_SNAI`); ADD TO NEXT TIME appends "• title" to the latest session's `nextTime` with `logsessionnext` (UNDO removes that line). Topic chip lists per type in `LS_SNTOPICS` (BK_KEYS; defaults `DEF_TOPICS`, invented, generic). Never add sessions to the ASK snapshot, the briefing, the Ship's Year, ASTROMETRICS, REVIEW or COMPUTER's index (COMPUTER has one action that sets `logTab` and opens LOG). Tests: `bridge_sessions.test.js`, `mock_v24` `sesmode` / `stats.ses`, `app_e2e58`.
