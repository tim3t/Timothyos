## 1. Goals

### The problem
Three systems that never meet:

| System | Holds | Problem |
|---|---|---|
| Google Calendar | Work meetings | Work only |
| Paper planner | Everything non-work | Not searchable, not measurable |
| Notion | Big concepts, key dates | Navigation friction, drifted away |

### The goal
One full-screen iPad app that shows **how I am spending my life**, with a UI I fully control.

### Success criteria
1. I open TimothyOS every morning instead of the paper planner.
2. A paper-planner item gets into the system in **under 10 seconds**.
3. Each week I can see **hours by life area** and write a short reflection.
4. I can ask Claude about my schedule and projects, and it can act on my personal data.

### Non-goals
- Multi-user, sharing, or collaboration.
- Replacing Google Calendar or Notion as storage. TimothyOS is the **front end**; they remain the backends.
- Writing to the work calendar. Ever.
- Home Assistant in the first release (architecture ready, not built).

## 2. Key terms

| Term | Meaning |
|---|---|
| **PWA** | Progressive Web App. A website that installs to the iPad home screen and opens full-screen like a native app. |
| **Life area** | A category of life: Work, Farm & Bees, Hobbies & Projects, Personal. Each has one color and one data source. |
| **Source** | Where an area's data comes from (a Google Calendar, an ICS feed, a Notion database). |
| **Integration module** | A self-contained plug-in on the server that talks to one outside service. Adding Home Assistant later = adding one module. |
| **Tailscale** | A free private-network app. Your iPad and NAS join a private "tailnet." TimothyOS is only reachable inside it. |
| **Capture queue** | A list on the iPad of items captured while offline. Sent to the server automatically when back online. |
| **Snapshot** | The last-synced copy of your day, week, and key dates, stored on the iPad for offline viewing. |

## 4. Life areas (configuration)

Life areas live in one config file (`config.yaml`), not in code. Add, rename, or recolor without a rebuild.

| Area | Color token | Source | Writable |
|---|---|---|---|
| Work | `--area-work` (periwinkle) | Work calendar (per D4 ladder) | **No (hard block)** |
| Farm & Bees | `--area-farm` (honey amber) | Google Calendar "TOS · Farm & Bees" | Yes |
| Hobbies & Projects | `--area-hobby` (coral) | Google Calendar "TOS · Hobbies" | Yes |
| Personal | `--area-personal` (teal) | Google Calendar "TOS · Personal" | Yes |

**Why "Personal" was added:** the paper planner holds errands, appointments, and family items that are neither farm nor hobby. Without a catch-all, quick capture would force a wrong choice. Remove it in config if unwanted.

**Area = calendar.** Every event's life area is known from which calendar it lives in. No tagging step, so weekly-review hours are automatic.

## 6. Data flow

```
                    ┌──────────── iPad (PWA, full-screen) ───────────┐
                    │  UI (Svelte)                                   │
                    │  Service worker: caches app shell              │
                    │  IndexedDB: snapshot + capture queue           │
                    └──────────────────────┬─────────────────────────┘
                                           │ HTTPS inside Tailscale only
                                           ▼
┌──────────────────── NAS (Docker) ─────────────────────────────────────┐
│  TimothyOS server (Python, FastAPI)                                   │
│   ├─ JSON API  (/api/today, /api/week, /api/capture, /api/ask ...)    │
│   ├─ Sync scheduler (every 5 min + on demand)                         │
│   ├─ Integration modules                                              │
│   │    ├─ google_calendar  (personal calendars, read/write)           │
│   │    ├─ work_calendar    (read-only: shared, ICS, or busy)          │
│   │    ├─ notion           (notes, priorities, key dates, reviews)    │
│   │    ├─ claude           (Ask panel, tool use)                      │
│   │    └─ home_assistant   (LATER, slot reserved)                     │
│   └─ SQLite: cache, action log, sync state, Google token              │
│  Secrets: .env file on NAS volume (never sent to browser)             │
└───────┬───────────────────┬───────────────────┬───────────────────────┘
        ▼                   ▼                   ▼
  Google Calendar API   Notion API        Anthropic API
```

### 6.1 Read path (opening the app)
1. iPad shows the cached snapshot instantly (marked with sync age).
2. iPad requests fresh data from the server.
3. Server answers from its SQLite cache (fast, no waiting on Google or Notion).
4. Background sync keeps the cache within ~5 minutes of the sources.

**Why a server-side cache:** Notion's API is rate-limited (about 3 requests/second average) and slower than a dashboard should feel. The cache makes every screen load fast and keeps API usage low.

### 6.2 Write path (capture)
1. iPad gives each capture a unique ID and stores it in the capture queue.
2. iPad sends it to `/api/capture`. Server writes to Google or Notion.
3. On success, server returns OK and iPad removes it from the queue.
4. If offline or failed, it stays queued and retries when the app regains connection, on app open, or when the app returns to the foreground.
5. The unique ID prevents duplicates if a retry happens after a success.

**iOS note:** Safari has no background sync, so the queue flushes when the app is open. The status light shows the pending count.

### 6.3 Data ownership

| Data | Lives in | TimothyOS role |
|---|---|---|
| Work meetings | Employer calendar | Read-only mirror |
| Personal events | Personal Google Calendars (one per area) | Read + write |
| Notes, priorities, key dates, projects, weekly reviews | Notion databases | Read + write (hidden backend) |
| Cache, action log, sync state | SQLite on NAS | Owns (rebuildable, except action log) |
| Snapshot, capture queue | iPad IndexedDB | Owns (temporary) |

Nothing important lives only in TimothyOS. If the NAS died, your calendars and Notion data are intact.

## 7. Integrations

### 7.1 Google Calendar (personal)
- **Library:** `google-api-python-client` + `google-auth-oauthlib` (official).
- **Account:** your personal Google account. Create calendars "TOS · Farm & Bees", "TOS · Hobbies", "TOS · Personal".
- **Scope:** calendar read/write.
- **Token:** one-time OAuth sign-in; refresh token stored server-side.
- **Gotcha (important):** a Google OAuth app left in **"Testing"** status issues refresh tokens that expire after **7 days**. Set the app to **"In production"** (unverified is fine for personal use; you click past one warning screen once).
- Bonus: these calendars also appear on your iPhone's built-in calendar.

### 7.2 Work calendar (read-only ladder)
Tried in order during Phase 0. Use the first that works.

| Rung | Method | Detail level |
|---|---|---|
| 1 | Share work calendar to personal Google account | Full titles and times |
| 2 | Secret ICS/iCal feed URL, polled every 10 min | Full titles and times |
| 3 | Free/busy only (share as "see only free/busy") | "Busy" blocks, still counted in hours |

- The `work_calendar` module has **no write functions at all**. Read-only is enforced by absence, not by a setting.
- If your employer's policy forbids all three, Work becomes a manual "Work block" area. Check your employer's policy before Rung 1 or 2.
- ICS parsing: `icalendar` + `recurring-ical-events` (handles repeating meetings).

### 7.3 Notion (hidden backend)
- **Library:** `notion-client` (well-maintained Python client for the official API).
- **Access:** an "internal integration" token, shared only with a "TimothyOS" page that holds these databases:

| Database | Key properties |
|---|---|
| Notes | Title, Body, Area, Created, Source (capture / claude) |
| Priorities | Title, Date, Area, Done |
| Key Dates | Title, Date, Area, Type (deadline, season, birthday ...) |
| Projects | Name, Area, Status, Next step |
| Weekly Reviews | Week, Hours per area (numbers), Went well, Drained me, Next focus, Claude summary |

- Existing Notion content can be moved or linked into these databases once during Phase 0.

### 7.4 Claude API (Ask panel)
- **Library:** official `anthropic` Python SDK.
- **Model:** `claude-opus-5-5`, effort `medium` for chat. Server-side refusal fallback enabled (`fallbacks: "default"`).
- **How it works:** tool use. Claude gets a small set of tools; the server runs them.

| Tool | Does |
|---|---|
| `list_events(range, areas)` | Read events from any area, including Work |
| `create_event / update_event / delete_event` | Personal area calendars only |
| `search_notion(query)` | Search notes, projects, key dates |
| `create_note / add_priority / add_key_date / update_project` | Write to Notion |
| `get_week_hours(week)` | Same numbers as the Review screen |

- **Guardrails (enforced in server code, not just the prompt):**
  1. **Work is unwritable.** Tools reject any Work target, and the work module has no write path.
  2. **Action log.** Every Claude write is recorded with a before/after copy in SQLite.
  3. **One-tap undo** from the panel for each logged action.
  4. **Delete limit.** At most 5 deletes per conversation turn; more triggers a "confirm" card.
- **Cost estimate:** Opus 5.5 is $4 per million input tokens, $20 per million output. A typical question (~8k tokens of context, short answer) is about 3 to 5 cents. At ~10 questions/day, roughly **$10 to $15/month**, lower with prompt caching (enabled for the system prompt and tool list).

### 7.5 Home Assistant (LATER, designed for, not built)
Every integration is a module with the same shape:

```
Integration
  name, area(s), poll_interval
  sync()          -> pull fresh data into cache
  panels()        -> optional UI cards for Bridge
  claude_tools()  -> optional tools for Ask panel
  health()        -> green / amber / red for Systems screen
```

Adding Home Assistant = one new module (REST API + long-lived access token, same home network as the NAS), plus its panel. Ideas: hive scale weight, greenhouse temperature, irrigation status, frost alerts. No changes to the core.

## 8. Security and secrets

| Item | Approach |
|---|---|
| Network | App listens only on the Tailscale interface. Not reachable from the internet |
| HTTPS | `tailscale serve` provides a real certificate for `timothyos.<your-tailnet>.ts.net`. (iOS requires HTTPS for PWA offline features) |
| Login | None. Tailscale device identity is the lock. Optional later: Tailscale ACL limiting the app to your iPad and laptop |
| Secrets | `.env` file on the NAS data volume, readable only by the app. Holds Google client secret, Notion token, Anthropic key |
| Browser | Never receives any secret or token. All outside API calls happen on the server |
| Git | `.env`, `*.db`, `config.yaml` (real IDs) are gitignored. Only `config.example.yaml` is committed |
| Backups | NAS snapshot of the data volume (SQLite + `.env`). Core data is already safe in Google and Notion |
| Lost iPad | Remove it from Tailscale admin. Access ends immediately |

## 9. Tech stack

Chosen to match the pattern you already maintain in Audio-Archive (Python core, local JSON API, thin browser UI).

| Layer | Tool | Why (plain language) |
|---|---|---|
| Server language | **Python 3.12** | You already write and maintain Python |
| Web server/API | **FastAPI** | Small, very well documented, auto-generates API docs page for debugging |
| Background sync | **APScheduler** | Runs "sync every 5 minutes" inside the server. No extra service |
| Database | **SQLite** | One file, no database server to run or upgrade |
| UI framework | **Svelte (via Vite)** | Plain-looking HTML/CSS with small reactive scripts. Full control of every pixel, little boilerplate. Builds to static files the Python server serves |
| PWA + offline | **vite-plugin-pwa** (Workbox) | Generates the service worker and install manifest for you |
| iPad storage | **IndexedDB via `idb-keyval`** | Tiny wrapper for snapshot and capture queue |
| Styling | **Plain CSS with design tokens** | No CSS framework to fight. LCARS shapes are just rounded rectangles |
| Font | **Antonio** (open-source condensed), self-hosted | Condensed LCARS-like feel, works offline |
| Packaging | **Docker + docker compose** | One command to start, update, or roll back on the NAS |

**Considered and rejected:**
- *Next.js / React:* more moving parts and churn than a single-user app needs.
- *One-language SvelteKit (JS everywhere):* reasonable, but moves you off Python for the parts with the most logic (sync, Claude tools).
- *htmx only, no JS framework:* simplest, but the offline queue and timeline interactions need real client-side code anyway.

### 9.1 Visual system (LCARS-inspired, original)
- **Background:** near-black. **Frames:** thick rounded "elbow" bars in muted tones.
- **Color = meaning.** Each life area owns one color, used everywhere for that area. UI chrome uses a separate neutral set so area colors stay readable.
- **Type:** Antonio, uppercase labels, 3 sizes only (label, body, display).
- **Touch:** minimum 56 px targets; Capture button ~88 px tall.
- **Noise budget:** no icons where a word works; no animation except the "now" line and sync light.
- **Original:** no copied Star Trek graphics, sounds, or numbering gimmicks. Shapes and palette are inspired, not traced.
- All colors defined as CSS tokens in one file for easy re-theming.

## 10. Hosting

### 10.1 Recommendation: **NAS with Docker, reached through Tailscale**

### 10.2 Comparison

| Factor | NAS (Docker) | Raspberry Pi | Cloud host (e.g. Fly.io) |
|---|---|---|---|
| Monthly cost | $0 | $0 (plus ~$80 up front if buying SSD/case) | ~$5 to $10 |
| Upkeep | Low. Already always-on, already backed up | Medium. SD cards fail; needs SSD + OS updates | Low hardware, but platform changes and billing to watch |
| Reliability | High (RAID, UPS if you have one) | Medium | High |
| Security | Strong. Private, no internet exposure | Strong (same Tailscale setup) | Weaker by default. Must add Tailscale or public login |
| Away from home | Yes, via Tailscale | Yes, via Tailscale | Yes, natively |
| Home Assistant later | Same network, easy | Same network, easy | Needs tunnel back home |
| Your data | Stays home | Stays home | On a third party's server |

**Why NAS wins:** zero added cost, already always-on and backed up, private by design, and Home Assistant will be on the same network.

**Requirement:** the NAS must run Docker (Synology "Container Manager", QNAP "Container Station", TrueNAS, Unraid all do). **If it cannot,** use the Raspberry Pi with a USB SSD (not an SD card). Same Docker setup, no design change.

**Away-from-home caveat:** if home internet or the NAS is down, the app shows the cached snapshot and queues captures. This matches D5.

## 12. Open risks

| Risk | Impact | Mitigation |
|---|---|---|
| Employer blocks all work-calendar sharing | No work meetings shown | Rung 3 or a manual "Work block" area |
| Google token expires weekly | Sync stops | Set OAuth app to "In production" (Phase 0) |
| Notion API slow or rate-limited | Laggy screens | Server cache; UI never waits on Notion directly |
| iOS PWA quirks (storage, no background sync) | Queued items wait until app opens | Flush on open/foreground; pending count always visible |
| Claude writes something wrong | Bad data in calendar or Notion | Action log + one-tap undo; Work unwritable; delete limit |
| NAS down while away | No fresh data | Cached snapshot + capture queue |
